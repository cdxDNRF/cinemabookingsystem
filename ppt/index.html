3 种角色 14 张数据表 19 个前端页面 11 个后端模块 30 部真实电影 8×8 在线选座

先给大家一个整体印象。我们这个系统，简单说就是一个完整的电影购票平台，覆盖了三类用户的所有核心需求。

左边这张卡是普通用户端。用户能做什么？浏览电影——我们数据库里预置了 30 部真实电影，海报是从 TMDB 获取的；可以按类型、年代、地区筛选；点进去看详情、看预告片、收藏、评分；最核心的是在线选座购票——8 乘 8 的座位图，点选座位、下单、支付，完整的购票流程。还有订单管理和自主注册注销。

中间是影院管理员端。影院工作人员可以管理影院信息、增删影厅、安排排片——这里有一个重要的冲突检测机制，同一影厅同一时间段不能重复排期。他们还可以查看自己影院的订单。不过影院管理员不是随便注册就能用的，需要超级管理员审核通过才行。

右边是超级管理员端，权限最高。审核影院入驻、管理所有电影、审批排期、看全平台订单、发布公告、管理账号，还有一个 ECharts 数据统计面板。

底下这些数字大家可以看一下：3 种角色、14 张表、19 个页面、11 个后端模块——规模不小，但架构很清晰。

这张图展示了我们的三层技术架构。

最上面是展示层，也就是前端。我们用了 Vue 3 的组合式 API，搭配 TypeScript 保证类型安全，UI 组件库是 Element Plus，构建工具是 Vite，状态管理用 Pinia。这一层的职责就是把数据好看地呈现给用户。

中间是业务层，也是核心。Spring Boot 3 提供 RESTful API，MyBatis 负责和数据库交互，JWT 做无状态认证——用户登录后拿一个 Token，之后每次请求都带着，后端不用存 Session。还有一个定时任务模块，专门扫描超时未支付的订单，自动释放座位。

最下面是数据层，MySQL 8.0，14 张表，全部用了外键约束保证数据完整性。还有一个关键设计——冗余缓存：电影表里直接存了票房总额和平均评分，不用每次查询都做聚合计算，性能提升很明显。

三层之间通信方式：前端和后端通过 HTTP REST 接口、JSON 格式、JWT Token 鉴权；后端和数据库通过 MyBatis 映射。真正做到了前后端完全分离，可以独立开发、独立部署。

权限实现：后端 @RequireRole 注解 + 拦截器 ｜ 前端 Vue Router 导航守卫 + meta.roles

系统设计这块，我重点讲两个维度：权限体系和数据库。

权限方面，我们设计了三种角色，层级非常清晰。最上面是超级管理员，紫色标识——能审核影院入驻、管理电影、审批排期、看全平台数据统计、发公告、管账号。中间是影院管理员，橙色——管理自己影院的信息、影厅、排片，看本影院订单。注意，影院管理员需要超级管理员审核通过后才能用，这是一个真实的业务审批流程。下面是普通用户，绿色——浏览电影、选座买票、收藏评分、看订单、自主注册注销。

权限怎么实现的呢？前后端各有一层防护。后端用自定义的 @RequireRole 注解加 AuthInterceptor 拦截器，声明式权限控制，哪个接口需要什么角色一目了然。前端用 Vue Router 的导航守卫，路由配置里写 meta.roles，进入页面前自动检查，角色不对直接跳转。两层防护，确保安全。

数据库方面，一共 14 张表，核心关系是这样的：超级管理员审核影院管理员，影院管理员管理影院、影厅、排期，排期关联电影，用户下单关联排期，订单展开到具体座位。电影和类型是多对多关系，通过中间表关联。还有一个设计亮点——电影表冗余缓存了票房和评分字段，避免每次查询做聚合。

这一页是今天的核心内容——业务流程。

先看上面四步，选座购票的完整闭环。第一步，用户浏览电影，选一个场次。第二步，进入 8×8 座位图，灰色是已售、白色可选、蓝色是你选中的——实时状态，不会出现两个人选同一个座位。第三步是最关键的——下单即锁座。你一提交订单，座位就被锁定 10 分钟。10 分钟内付款，订单正常流转；超时没付，后端定时任务自动取消订单、释放座位。这就解决了并发选座的问题。第四步，支付后去影院取票，流程结束。

左下角是排期管理流程。影院管理员提交排期的时候，系统会自动做冲突检测——查同一影厅在目标时间段有没有重叠的排期。SQL 条件是：新排期开始时间小于已有排期结束时间，且新排期结束时间大于已有排期开始时间。有冲突就报错，没冲突才保存。保存后还要等超级管理员审核通过，用户才能看到这个场次。

右下角是审核工作流。影院管理员不是注册就能用的——先注册、提交影院信息、等待审核，超级管理员审批通过后才绑定影院 ID、正式启用。排期也是同样的逻辑，提交后等审核。

这三个流程串起来，就是一个从管理到消费的完整业务闭环。

// part 06 · key techniques

四个关键技术点

01
🔐 JWT 无状态认证 + 双层权限控制

登录后签发 JWT Token 存 localStorage，每次请求 Header 携带。后端 AuthInterceptor 解析 Token → @RequireRole 注解声明式鉴权。前端 Vue Router beforeEach 导航守卫检查 meta.roles。公开页面（电影首页/详情）无需登录即可访问。

02
💺 锁座 + 超时自动释放

下单时座位状态变为"已锁定"，订单记录 lock_expire_time（当前时间+10分钟）。后端定时任务（@Scheduled）每分钟扫描超时未支付订单，自动取消并释放座位。使用数据库事务保证原子性。

03
📅 排期冲突检测

新增/编辑排期时，SQL 查询同影厅时间段是否重叠：start_time < #{endTime} AND end_time > #{startTime}。存在重叠则返回错误，阻止保存。数据库层加唯一约束双重保障。

04
⚡ 冗余缓存策略

电影表冗余存储 total_box_office、rating_avg、rating_count。用户评分或订单完成时实时更新缓存字段。避免每次查询做聚合计算，以空间换时间，显著提升首页和列表页查询性能。

技术实现这块，我挑四个最有代表性的点深入讲。

第一个，JWT 认证加双层权限控制。用户登录后后端签发一个 JWT Token，前端存 localStorage，之后每次请求自动带在 Header 里。后端有个 AuthInterceptor 拦截器，拦截所有 /api 请求、解析 Token、把用户信息注入上下文。然后通过 @RequireRole 注解做声明式权限控制——比如某个接口加 @RequireRole("ADMIN")，就只有超级管理员能调。前端也有独立的一层：Vue Router 的 beforeEach 导航守卫，根据路由 meta.roles 配置检查当前用户角色，不匹配就跳转。两层防护，缺一不可。

第二个，锁座和超时释放。这是购票系统最核心的并发问题。用户下单那一刻，座位就被标记为已锁定，订单记录一个 lock_expire_time——当前时间加 10 分钟。后端有个 @Scheduled 定时任务，每分钟扫一遍超时未支付的订单，自动取消、释放座位。整个过程在数据库事务里完成，保证原子性。

第三个，排期冲突检测。SQL 条件就一行，但逻辑很精妙：新排期开始时间小于已有排期结束时间，且新排期结束时间大于已有排期开始时间——两个时间段有交集就是冲突。数据库还加了唯一约束做双重保障。

第四个，冗余缓存。电影表里直接存了票房和评分，每次有人打分或买票就更新这个字段。代价是写操作多了一步更新，但读操作省了聚合计算——而读的频率远高于写，所以整体性能提升很明显。

最后一页，做一个总结。

左边是已完成的功能，一共九大项。从三角色权限体系，到电影浏览搜索、在线选座购票、订单管理、审核工作流、排期冲突检测、数据可视化、公告账号管理，再到收藏评分和用户注册注销——一个电影购票平台该有的核心功能，我们基本都覆盖了。

项目有几个突出特色：前后端完全分离，可以独立开发独立部署；审核工作流模拟了真实业务场景，不是简单的增删改查；排期冲突检测和锁座超时释放这两个机制解决了实际业务中的并发和数据一致性问题；冗余缓存策略体现了性能优化的意识；真实电影海报提升了用户体验。

右边是可扩展方向，也是这个项目未来可以继续完善的地方。最直接的就是接入微信支付或支付宝，把模拟支付变成真实支付；座位图可以做得更灵活，不限于 8 乘 8；可以加推荐算法；加消息通知系统；加用户评论回复功能。这些都是锦上添花的方向。

总的来说，这个项目完整实现了一个电影购票系统的核心业务闭环，技术栈主流、架构清晰、代码规范。对我来说，通过这个项目深入理解了前后端分离开发的全流程，也锻炼了系统设计的能力。
